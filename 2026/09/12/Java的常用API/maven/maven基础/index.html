GVAP

  • G：group标签，组号
  • V：version标签：版本号
  • A：artifactId：地址号
  • P：打包方式，默认jar,倘若作为父类，则必须是pom

依赖冲突

先理解一个概念
依赖传递（只有作用范围为compile的可以传递）
一个依赖的引入会同时带来他所必须的依赖

依赖是有版本的，随着依赖数量的增多，必然会出现同一个依赖有不同的版本
这就是依赖冲突

maven如何解决依赖冲突？

自由选择原则

短路优先
  • 第一条链路：A依赖B，B依赖C，C依赖D
  • 第二条链路：E依赖F，F依赖D
  • 可以看出，两者都依赖D，而第二条更近，所以选择第二条的D
先声明
  • 如果第短路优先无法选出，那么先声明的优先
  • 直接来说，在上面的优先

手动排除

  • 通过exclusion标签进行排除
    示例：

继承

为什么要继承
如果一个项目中有多个模块,每个模块的版本之间管理就会很麻烦
这时候用继承机制
创建一个父模块，用来管理版本
子模块如果在写依赖的时候就可以省略版本信息，直接用父类声明好的版本

继承示例：

父项的打包方式必须是pom

子项通过parent标签来声明继承关系

只要是父工程中依赖会被无条件的继承给子工程，和依赖传递的范围限制无关

版本声明，具体是使用properties这个标签

<properties>

  • 声明属性，如Java的版本，依赖的版本
  • 使用声明的版本可以通过${}符
  • <junit.version>这个标签的名字是自定义的

依赖范围

依赖范围

  • 编译环境（核心代码）
  • 测试环境（测试代码）
  • 运行环境（打包）

compile

  • 默认 ，在三种环境中都生效

test

  • 只对测试环境有效

provide

  • 已提供依赖范围，对编译和测试有效

runtime

  • 对测试，运行有效

system

  • 对编译测试有效，在使用非仓库所有的依赖时使用，需要提供jar包在本地计算机的地址

import

  • 导入依赖范围 该依赖范围只能与 dependencyManagement 元素配合便用
